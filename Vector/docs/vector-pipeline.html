● Vector GTM Engine — technical walkthrough

How the Vector pipeline runs
— and how it reaches the dashboard

A plain-English tour of what happens from the moment you start the engine on the backend, through every stage and AI agent, to the exact way accounts, people, campaigns and analytics light up in the CRM.

★The short version

Vector is a go-to-market (GTM) engine. You give it an ideal-customer profile; it goes and finds companies that are showing "buying signals" (like raising money or hiring), figures out who the decision-makers are, drafts personalized outreach for email + LinkedIn, and records everything so your team can watch the pipeline in a clean dashboard.

It has three modules, each a small team of AI agents:

ModuleJobReal-world analogy
ScoutFind companies & the right peopleA researcher who reads the news and LinkedIn all day
PulseWrite & run email + LinkedIn sequencesAn SDR who never forgets a follow-up
CompassDeal / meeting guidance (planned)A sales manager reviewing next steps

Everything a run discovers is saved to one SQLite database, and the CRM reads that database through a read-only API. The frontend never controls the engine — it only shows what the engine found.

1How a run is triggered

Runs are a backend-only action. There is no button in the app, and the trigger endpoint doesn't exist — the only way to start the engine is a command on the server:

# Start a live run for one workspace (account), find up to 6 companies
python -m backend.manage run-pipeline --email team@vector.ai --max-leads 6

That command does three simple things before any AI runs:

  1. Looks up the account and its workspace (every account has its own isolated workspace).
  2. Refuses to run on the demo account (that one is pre-filled sample data and stays read-only).
  3. Creates a PipelineRun row with status = "running" so progress can be tracked.
Why backend-only?

Live runs spend money (LLM calls) and touch the outside world (news sites, search). Keeping the trigger on the server means no accidental clicks, no runaway costs from the UI, and a single audited place where runs begin.

The frontend can watch, not touch

The UI polls GET /api/pipeline/runs every few seconds purely to display a live run's stage and counts. That's a read. It cannot start, stop, or change a run.

3Stage 0 — the run is created

0

A single row is inserted so the whole run is trackable and the UI can show progress. Think of it as the "job ticket".

# pipeline_runs table row
{ id: 1, workspace_id: 2, status: "running", stage: "queued",
  companies_found: 0, people_found: 0, enrolled: 0, messages_sent: 0,
  started_at: "2026-07-22T15:00Z" }

As each later stage completes it updates these counters, so a half-finished run still shows real numbers.

4Stage 1 — Scout · Radar finds companies

1

Radar reads recent tech news, decides which articles describe a real company doing something noteworthy (a "buying signal"), and scores how well that company fits your ideal customer profile (ICP). Code entry point: NewsRadarPipeline.run().

The agents involved

SelectorAgent
Looks at a news page's HTML and figures out where the article links/headlines are.
HTML → CSS selectors
LeadExtractionAgent
Reads an article and extracts: is this a lead? which company? what signal?
article → LeadInsight
CompanyEnricher
Finds the company's website & LinkedIn URL.
name → website, linkedin
ICPRatingAgent
Scores fit 0–100 & tier A–D, with reasons for and against.
insight → ICPRating
Real example

Article: "Supabase hit $5B by turning down million-dollar contracts."

→ LeadExtractionAgent says: company = Supabase, signal = funding.
→ ICPRatingAgent says: score 38, tier C, "strong funding signal, but core product is a database, not an AI-agent platform."

What gets saved

For each qualified company (score ≥ 35), the run writes a Company row plus its Signal history and the ICP reasons (as ICPCriterion rows). The run's companies_found counter ticks up live.

# one Company + nested rows
Company  { name:"Supabase", slug:"supabase", signal_type:"funding",
           icp_score:38, icp_tier:"C", qualified:true, website_url:"supabase.com" }
Signal   { signal_type:"funding", headline:"Supabase hit $5B…", confidence:0.85 }
Criteria { kind:"matched", text:"Strong funding signal — budget available" }

5Stage 2 — Scout · Detective finds people

2

Now that we have companies, Detective finds the decision-makers at each one (Founder, CEO, CTO, Head of AI, VP Eng, Head of Product) and tries to get a real, verified email. Code entry point: DetectivePipeline.run().

The agents involved

ProfileFinder
Web-searches for people in target roles at the company.
company + roles → candidates
ProfileExtractionAgent
Turns messy search results into clean people: name, title, LinkedIn, confidence.
results → DecisionMaker[]
EmailFinder
Finds/guesses the email & marks it verified / guessed / unverified (via patterns, Apollo/PDL, MX checks).
person → email + status
Real example

For Supabase, Detective returns Paul Copplestone — CEO, LinkedIn found, email paul@supabase.com marked verified (95% confidence).

Email finding — providers

By default the finder is keyless: it generates likely address patterns, SMTP-verifies them, and cross-checks Gravatar → so emails come back verified / guessed / unverified. Two premium providers, Apollo and PDL, are fully built and switch on via one config setting (they consume API credits, so they stay off unless enabled).

What gets saved

Each person becomes a Person row linked to its company, plus a timeline Event ("Identified as CEO at Supabase"). The people_found counter updates.

Person { name:"Paul Copplestone", role_category:"CEO", email:"paul@supabase.com",
         email_status:"verified", linkedin_url:"/in/paulcopplestone", company → Supabase }
Event  { type:"decision_maker_found", title:"Identified as CEO at Supabase" }

6Stage 3 — Pulse · Campaigns builds outreach

3

Pulse turns people into outreach. It makes sure the workspace has a Campaign, and every campaign owns two sequences: one for Email and one for LinkedIn. Each sequence is a series of steps, and each step can have A/B message variants.

The structure it creates

Campaign  "Outbound — Qualified Leads"
 ├─ Sequence (email)     → Step 1 Intro → Step 2 Value → Step 3 Bump → Step 4 Breakup
 │                          each Step has Variant(s): subject + body templates
 └─ Sequence (linkedin)  → Step 1 Invite → Step 2 Intro msg → Step 3 Value → Step 4 Breakup
                            (invite must be accepted before messaging)

Then Pulse runs its autopilot cycle — the fully autonomous outreach loop. It's the real engine, not a simplified stand-in, so every safety and optimization behavior below is active:

Scheduler (per channel)
Advances each person step-by-step, waiting wait_days between touches. Only sends inside the send window (8–18, Mon–Fri).
due people → next step
Warmup + caps
A new mailbox sends only 10/day, ramping +5/day to a 40 cap (LinkedIn: 5 → +3 → 20 invites; 40 msgs). Protects deliverability.
mailbox → today's allowance
WriterAgent / FollowUpAgent
LLM-writes each email personalized to the person + signal (not a static template).
person → subject/body
A/B bandit (Thompson)
Picks the best-performing message variant per step and auto-promotes a winner once it's statistically ahead.
variants → winner
LinkedIn accept gate
Sends an invite, waits for acceptance, then messages. Expires stale invites after 21 days.
invite → accept → message
ReplyClassifier + ConversationAgent
Reads replies, classifies them (interested / objection / OOO / unsubscribe…), and drafts the right response — or escalates to a human.
reply → action
SchedulingAgent
When someone's interested, proposes real open calendar slots and books the meeting.
reply → booked meeting
Real example — for Paul

Day 0: email step 1 (LLM-written) sent + LinkedIn invite sent. Day 3: follow-up email; invite accepted → intro message. Paul replies "interested" → ConversationAgent answers and the SchedulingAgent offers 3 slots → books a 30-min intro call. The winning subject-line variant gets promoted for everyone else.

Master safety switch — nothing is sent by default

All of the above runs in SAFE mode unless VECTOR_PULSE_LIVE=1 is set on the server:

• Email: dry-run — messages advance state (steps, threading, warmup, A/B stats) but no SMTP/IMAP socket is ever opened.
• LinkedIn: a mock provider simulates invites/accepts/replies — no real LinkedIn traffic.
• Calendar: a mock calendar — no real events.

So a pipeline run exercises the entire autonomous system end-to-end and fills the CRM with realistic state, while sending exactly nothing. Flipping the one switch to 1 (with mailbox / LinkedIn / calendar credentials) is what makes it send for real.

7Stage 4 — the run finishes

4

The run row is stamped status: "succeeded", stage: "done", with final counts and a finish time. If any stage throws (bad network, missing key, a news site blocking scraping), the run is marked failed and the exact error is stored — the UI shows it plainly instead of pretending it worked.

{ status:"succeeded", stage:"done", companies_found:5,
  people_found:11, enrolled:14, messages_sent:14,
  finished_at:"2026-07-22T15:07Z" }

8Where everything is stored

One SQLite database (data/vector.db) holds it all — no scattered JSON files. Every row belongs to a workspace, so the demo account and each real account are fully separated.

TableHoldsFilled by
workspaces / usersAccounts & isolationBackend account setup
companies, signals, icp_criteriaAccounts & why they fitRadar
peopleDecision-makers & emailsDetective
campaigns → sequences → sequence_steps → variantsOutreach plays (email + LinkedIn)Pulse
enrollments, messagesWho's in a sequence + drafted messagesPulse
eventsThe activity timelineEvery stage

The bridge to the UI

A FastAPI server exposes this database as read-only JSON endpoints (/api/companies, /api/people, /api/campaigns, /api/dashboard, /api/analytics…). The CRM only talks to these endpoints.

Two ways the data appears

  1. On page load / navigation: each page calls its endpoint — People → GET /api/people, Companies → GET /api/companies, a campaign → GET /api/campaigns/{id}, and so on. Filters, search and paging are query params, so the server does the filtering (fast, even with lots of rows).
  2. While a run is happening: a small provider polls GET /api/pipeline/runs. When it sees a run flip from running to succeeded, it bumps an internal dataVersion counter. Every page listens to that counter and silently re-fetches — so new companies/people "appear" without a manual refresh.
Plain-words version

The engine fills a database. The website keeps asking the database "anything new?" and redraws when the answer changes. The website itself never does any GTM work — it just paints the latest picture.

The one thing the UI can change

You can edit a sequence's message (subject/body of a variant) and pause/activate a campaign. Those are the only writes, they go to PATCH endpoints, and they're blocked on the demo account. Nothing about editing a draft sends it.

10How analytics & the dashboard are handled

Nothing is precomputed or faked. When you open Analytics or the Dashboard, the API runs quick counting queries over your workspace's rows and returns tidy numbers the page draws as KPIs, a funnel, and a campaign table.

12Safety & guarantees

✓ The frontend cannot trigger a run. No button, and the trigger endpoint returns 404. Login, reload, navigation and polling are all read-only.

✓ No signup. Accounts are created only from the backend; the UI is sign-in only.

✓ Nothing sends unless one switch is on. The full autonomous engine (multi-step sequencing, warmup, caps, send-window, A/B bandit, reply handling, meeting booking) is wired into the pipeline, but runs in SAFE mode — dry-run email, mock LinkedIn, mock calendar — until VECTOR_PULSE_LIVE=1 is set on the server.

• Runs are paused until you explicitly ask to run one. The demo account stays fully populated and untouched.
